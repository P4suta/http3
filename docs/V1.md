# First-publication gate

The first artifacts will use version `0.1.0`, but they qualify only after the
same functional, safety, performance, documentation, interoperability, and
audit standards expected of a stable v1 product are met.

A release candidate requires all of the following to be green:

- the stable standard-request/response, common body, error, client, server,
  context, middleware, diagnostics, and resource-controller contracts;
- complete HTTP/1.1, HTTP/2, HTTP/3, QUIC v1/v2, TLS 1.3, HPACK, and QPACK
  behavior in the declared scope;
- an empty HTTP/3-to-private-QUIC boundary allowlist;
- the dated RFC and errata inventory with every applicable MUST and SHOULD
  mapped to implementation, test evidence, or a reviewed non-applicability
  reason;
- line coverage of at least 95% and branch coverage of at least 90%, with
  direct tests for every public error, authentication, parser boundary,
  resource rejection, cleanup, and replay decision;
- PR-scale property, model, and fuzz campaigns and the million-case nightly
  campaign, including the declared hostile and crash scenarios, plus
  source-bound fresh-VM repetition for scheduling-sensitive regressions;
- bidirectional HTTP, QUIC, browser, MASQUE, and OHTTP interoperability;
- the OTP 28/29, operating-system, credential, mTLS, rotation, resumption, and
  rejection matrix;
- fixed cross-protocol throughput, tail-latency, memory, mailbox, idle-wakeup,
  and connection-release regression gates;
- typed redacted observations, finite sinks, and optional telemetry adapters;
- completed independent cryptographic, protocol, HTTP parsing, and resource
  exhaustion audits with no critical or high-risk findings; and
- exact `quic_core -> http3 -> http` dependency installation in an empty
  consumer, reproducible content-audited archives, SBOM, provenance,
  signatures, and secret/unwanted-file scans.

Current readiness is recorded in [CONFORMANCE.md](CONFORMANCE.md). Until every
applicable row is `Ready`, the packages remain development-only. Tagging,
version changes, Hex publication, pushes, and hosted releases require a later
explicit request and are not performed by these gates.

`mise run release-candidate` accepts a source candidate only when the current
source digest matches a completed deterministic audit bundle. An independent
attestation must be stored as `audit/third-party-attestation.json`, match that
source digest, and have a detached signature at the same path with `.sig`
verified by `gpgv` against `audit/trusted-auditors.gpg`. A signed `HEAD` counts
only when `git verify-commit HEAD` succeeds and the candidate worktree is
clean, including untracked files. A signature on an earlier commit cannot
qualify uncommitted candidate content.
