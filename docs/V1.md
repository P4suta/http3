# Public v1 completion gate

This document defines what must be complete before `http3` is considered ready
for its first public release. It is a quality and implementation gate, not a
version-number, tag, hosting, or package-publication milestone.

The existing client, server, and transport APIs are a tested bootstrap over the
external Erlang `quic` package. Completing those wrapper phases does **not**
complete v1. Public v1 requires this repository's own `gleam_quic` transport
core to be the only production backend and requires the external `quic`
dependency to be absent from the production dependency graph.

## Standards baseline

The baseline is frozen to published IETF standards available on 2026-08-23.
All normative requirements that apply to a general-purpose endpoint are in the
v1 gate; unsupported optional features must be explicitly identified and must
not be falsely negotiated.

| Layer | Required specifications and behavior | Status |
| --- | --- | --- |
| QUIC invariants and versions | [RFC 8999](https://www.rfc-editor.org/info/rfc8999), QUIC v1 [RFC 9000](https://www.rfc-editor.org/info/rfc9000), QUIC v2 [RFC 9369](https://www.rfc-editor.org/info/rfc9369), and downgrade-safe compatible version negotiation [RFC 9368](https://www.rfc-editor.org/info/rfc9368) | In progress |
| QUIC security | TLS 1.3 [RFC 8446](https://www.rfc-editor.org/info/rfc8446), QUIC-TLS mapping and packet protection [RFC 9001](https://www.rfc-editor.org/info/rfc9001), certificate paths [RFC 5280](https://www.rfc-editor.org/info/rfc5280), and service identity [RFC 9525](https://www.rfc-editor.org/info/rfc9525) | In progress: primitives, vectors, authentication, 1-RTT handshake, bounded HRR, post-handshake tickets, PSK resumption, replay/parameter-checked 0-RTT, and key lifecycle state models complete; certificate selection and live transport integration remain |
| Recovery and paths | Loss detection, PTO, NewReno, ECN, anti-amplification, Retry, stateless reset, connection-ID rotation, NAT rebinding, active migration, key update, IPv4 and IPv6 from [RFC 9000](https://www.rfc-editor.org/info/rfc9000) and [RFC 9002](https://www.rfc-editor.org/info/rfc9002) | In progress: pure models cover loss/PTO, NewReno, ECN, amplification, Retry, reset, CID rotation, and key update; live scheduling, sockets, and migration remain |
| Congestion and MTU | NewReno baseline, CUBIC [RFC 9438](https://www.rfc-editor.org/info/rfc9438), UDP safety [RFC 8085](https://www.rfc-editor.org/info/rfc8085), and DPLPMTUD [RFC 8899](https://www.rfc-editor.org/info/rfc8899) without IP fragmentation | In progress: NewReno, CUBIC, pacing, and PMTU probe models complete; live path integration remains |
| QUIC extensions | QUIC DATAGRAM [RFC 9221](https://www.rfc-editor.org/info/rfc9221) and QUIC-bit greasing [RFC 9287](https://www.rfc-editor.org/info/rfc9287) | Not complete |
| HTTP/3 | Complete client and server semantics, control streams, request streams, informational and final responses, trailers, push, GOAWAY and graceful drain from [RFC 9114](https://www.rfc-editor.org/info/rfc9114) | Bootstrap only |
| QPACK | Static and dynamic tables, blocked-stream limits, encoder and decoder streams, and Huffman coding from [RFC 9204](https://www.rfc-editor.org/info/rfc9204) | Bootstrap only |
| HTTP extensions | Extensible priorities [RFC 9218](https://www.rfc-editor.org/info/rfc9218), Extended CONNECT and WebSockets [RFC 9220](https://www.rfc-editor.org/info/rfc9220), and correctly associated HTTP Datagrams and bounded Capsules [RFC 9297](https://www.rfc-editor.org/info/rfc9297) | Bootstrap partial |

The implementation must consume verified errata for these documents. A row is
not complete merely because a peer accepts a happy-path request.

## Required product behavior

The stable v1 surface must provide all of the following without exposing PIDs,
atoms, maps, references, socket records, cryptographic key material, or mailbox
formats:

- bounded buffered and backpressured streaming clients and servers;
- reusable connections, concurrent streams, cancellation, typed protocol
  failures, total deadlines, keepalive, graceful draining, and deterministic
  cleanup;
- secure defaults, SNI and hostname verification, explicit trust stores,
  server certificate selection, session resumption, replay-safe 0-RTT, and
  automatic key update;
- QUIC v1 and v2, safe version negotiation, IPv4 and IPv6, path validation,
  NAT rebinding, active migration, ECN, PMTU discovery, NewReno and CUBIC;
- complete QPACK, request and response trailers, informational responses,
  server push, GOAWAY, Extended CONNECT, Capsules, RFC-conforming HTTP
  Datagrams, and RFC 9218 priority;
- bounded resource controls for every peer-controlled count, length, queue,
  stream, table, timeout, and amplification path;
- opt-in qlog, structured statistics, reproducible benchmarks, and enough
  diagnostic context to investigate protocol failures without secrets.

`HTTP Datagram` is not a generic unreliable side channel for ordinary GET or
POST requests. The v1 API must require semantics negotiated by an HTTP
extension, as required by RFC 9297. The current bootstrap interoperability
fixture that sends a Datagram on GET is test scaffolding, not the final API
contract.

## Draft protocol policy

Internet-Drafts are not stable v1 requirements. As of the baseline date this
includes WebTransport over HTTP/3, QUIC multipath, ACK Frequency, reliable
stream reset, extended key update, receive timestamps, and the qlog event
schemas. Implementations may be developed in clearly named experimental
modules pinned to an exact draft revision. Draft support must never alter the
stable protocol silently, and a draft changing or expiring cannot block the
standards-based v1 core.

Extended CONNECT, Capsules, HTTP Datagrams, and generic QUIC streams must be
sufficiently complete for separate WebTransport and MASQUE packages to build
above `http3`; those application protocols do not belong in the stable core.

## Implementation boundary

The native core lives in `packages/gleam_quic`. Protocol codecs, TLS transcript
coordination, transport state, stream and connection state machines, recovery,
congestion control, scheduling, and HTTP/3/QPACK behavior are Gleam code.

Erlang FFI is restricted to capabilities supplied by the runtime:

- UDP socket operations and address conversion;
- cryptographically secure randomness and monotonic time;
- constant-time cryptographic primitives and protected key storage; and
- X.509 decoding, signature operations, and certificate-path validation.

An FFI function must not parse or construct a QUIC, TLS, HTTP/3, or QPACK wire
message and must not own a protocol state machine.

## Verification gate

Every required row must pass all applicable gates before publication:

1. RFC example and boundary unit tests, state-model tests, property tests, and
   regression tests for every fixed defect;
2. deterministic virtual-network tests for loss, duplication, corruption,
   reordering, delay, MTU changes, migration, clock movement, and exhaustion;
3. real UDP loopback tests with fixed timeouts and process/socket convergence;
4. client and server interoperability against at least two independent QUIC
   implementations, for both QUIC versions where peers support them;
5. current QUIC and HTTP/3 interop/conformance runners, negative protocol
   tests, TLS vectors, QPACK vectors, and fuzzing with retained seeds;
6. load, long soak, memory/mailbox bounds, and reproducible benchmark evidence
   across supported OTP and operating-system matrices; and
7. a security review covering cryptographic usage, certificate validation,
   replay, amplification, denial of service, parser bounds, secret logging,
   and dependency/source audit.

The final cutover additionally requires zero production references to the
external `quic` application, a clean compiler public-interface audit,
`mise run check`, and a clean working tree after signed local commits.

Publication, tags, hosted releases, and Hex operations remain outside this
gate and require a separate explicit decision after all checks pass.
